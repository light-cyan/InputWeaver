# Phase 1 完成及 Weave v1 设计后的研究报告

## 报告范围

本文记录 2026-08-20 时 InputWeaver 的代码能力、Weave v1 语言设计覆盖、Windows 输入平台边界、安全基础、调试能力，以及从当前实现演进到通用映射和宏系统时适用的模块与层次划分。

## 总体结论

当前项目已经形成一个经过验证的 Windows 输入闭环底座：程序能够观察和规范化低级键盘与鼠标输入、区分输入来源、按目标进程和前台状态限制规则、通过带自身标签的 `SendInput` 产生输入、阻止自身输出递归触发规则，并在队列、注入、目标进程或关闭路径发生异常时保持有界、可清理和默认放行。

The executable mapping path currently consists of the four Phase 1 fixed rules. `docs/language/grammar.v1.md` defines complete mappings, event rules, conditions, variables, action flows, waits, branches, loops, asynchronous tasks, pause, cancellation, and output ownership. The Phase 2 contract and the compiler and runtime successor plans define the representation and complete implementation scope required to execute those semantics.

因此，Phase 1 的完成代表平台输入底座和安全隔离完成，而整个通用映射产品处于“底层实现完成、语言和运行时方案已设计、通用执行链等待实现”的阶段。

## 当前可运行能力

- 观察当前交互桌面中的低级键盘和鼠标输入，并规范化键盘按下与松开、鼠标按钮、移动、垂直滚轮和水平滚轮事件。
- 把输入分类为 `PhysicalCandidate`、`SelfInjected` 或 `ExternalInjected`，自身注入和第三方注入输入均不进入固定规则。
- 运行观察模式，保证不消费或生成输入。
- 运行目标限制的固定规则模式，其中 F6 映射为 F7、F7 映射为 F8、F9 映射为鼠标中键点击、物理鼠标中键映射为 F10。
- 按可执行文件名或绝对路径定位目标，保留目标进程句柄以确认身份、存活状态和完整性级别，并在目标重启后重新等待和定位。
- 只在目标拥有前台窗口时接受新映射；鼠标来源或鼠标输出还要求当前指针或捕获路由属于目标。
- 为所有程序生成的键盘和鼠标 `INPUT` 写入进程自身标签，并检查 `SendInput` 的完整、部分和失败返回。
- 使用固定容量单生产者单消费者队列把钩子决策和输入注入分离，钩子回调不执行文件 I/O、控制台 I/O、等待或输入注入。
- 队列满时放行触发输入，首次满队列会向主线程发送运行时错误事件并立即在控制台显示错误；全部拒绝次数继续保存在结束指标和 JSONL 诊断中，同一运行实例不会因持续满队列反复刷屏。
- 对部分注入生成带标签的配对清理输入，保留未解决的合成释放并进行有界重试，连续失败后打开熔断器并停止接受新捕获。
- 使用物理 Ctrl+Shift+F12 触发独立于目标、暂停状态和用户规则的受控停止。
- 使用固定容量诊断环和 8 MiB JSONL 上限记录规则、队列、注入、取消、清理、熔断、性能和可选隐私脱敏输入跟踪。

## Windows 平台能力边界

当前低级钩子观察的是交互桌面的系统输入流，`SendInput` 写入的也是系统输入流。目标进程检查能够缩小错误投递窗口，但前台检查、指针路由检查、物理状态检查和 `SendInput` 之间不存在一个绑定目标 PID 的原子 Windows 操作。

当前自身标签用于阻止意外递归，不构成经过认证的输入身份。没有 Windows injected 标志的事件被视为物理候选，因此低级钩子不能证明每个物理候选事件都来自真实人工设备。

当前实现覆盖普通交互桌面和用户态 `SendInput` 路径。后续能力目录应明确描述每个输入来源、控制名称和输出动作是否能够被当前 Windows 后端观察、消费或生成，并让编译器对后端不支持的能力给出确定诊断。

“通用映射”在本项目中的可操作定义应是：在已声明的控制集合、事件集合、动作原语和后端能力范围内，用户可以通过组合语言结构表达规则，而不需要为每种映射重新编写 C++。该定义允许以后增加新的 Windows 输入后端，同时保持 Weave 规则模型和通用运行时稳定。

## Weave v1 语言覆盖

Weave v1 已经定义以下语言构件：

- `TARGET`、`TAP_DURATION`、`ACTION_GAP` 和 `PAUSE` 内蕴配置或状态。
- `state`、`number` 和 `duration` 用户变量，以及具有静态类型的算术、比较和逻辑表达式。
- 键盘键和鼠标按钮的 `[held]`、`[idle]` 状态，以及状态值的 `[on]`、`[off]` 查询。
- `:down`、`:up` 和 `:repeat` 事件。
- 使用 `:=` 表达由运行时负责按下、重复和松开配对的完整生命周期映射。
- 使用 `=>`、`=>>`、`~>` 和 `~>>` 独立表达消费或放行、停止或继续扫描。
- `press`、`release`、`tap`、`wait`、`gap`、`set`、`toggle` 和 `exec` 动作。
- `if`、`repeat` 和 `while` 控制结构，以及每条匹配规则产生独立任务实例的异步执行模型。
- 取消代际、输出所有权计数、暂停切换清理、目标失效清理和强制停止清理语义。

这套设计已经覆盖通用键鼠映射和常见宏所需的主要组合原语。当前 v1 的鼠标语法以按钮为范围，鼠标移动、滚轮和连续坐标输入尚未进入语言控制目录。语言当前采用事件驱动的命令式 DSL，动作使用函数调用外观，表达式保持纯读取，整体认知模型比完整通用编程语言更贴近映射任务。

## 形式化与确定性

编程语言语法可以保持上下文无关；名称绑定、控制名称解析、变量类型和动作参数类型由语义分析处理。把这些语义约束交给编译器的符号和类型阶段，比把文法设计成上下文有关语言更容易得到可预测解析、清晰错误位置和稳定工具支持。

文法歧义和规则重叠需要分开处理。文法歧义表示同一记号序列具有多棵语法树；规则重叠表示同一输入事件同时满足多条已经正确解析的规则。v1 已使用源码顺序和四种箭头定义规则重叠的确定运行结果。

编译器实施前适合把当前规范性文字落实为以下机器可验证边界：

- 完整记号表、最长匹配规则和 UTF-8 限制。
- EBNF 产生式及运算符优先级和结合性。
- 带源码区间的 AST 节点结构。
- 名称空间、名称绑定和静态类型判断规则。
- AST 到表达式程序、动作程序和规则索引的确定降低规则。
- 规则分派、任务推进、取消和输出所有权的状态转移及不变量测试。

当前语言中需要在编译器实现前保持明确语义的易用性项目包括 `PAUSE[on]` 表示规则运行、四种箭头的组合含义、`|` 表示动作间隔、非整数 `repeat` 上限的迭代结果，以及 `exec` 对配置可信边界的影响。

## 推荐层次与依赖方向

```text
.weave source -> Compiler -> immutable CompiledProgram
                                      |
Windows Hook -> InputNormalizer -> RuleDispatcher -> TaskScheduler -> OutputOwnership -> InputBackend
                                      |
                                RuntimeState / MappingRuntime

TUI / CLI -> ApplicationController -> configuration, lifecycle, pause, reload, status
Diagnostics <- compiler, dispatcher, scheduler, application, platform
```

依赖方向应保证语言编译器和运行语义不依赖 Win32 头文件。Windows 层负责把平台结构转换成 core 类型，并通过窄接口提供输入注入、进程启动、目标身份、路由检查和时钟。

## 推荐模块职责

### `src/compiler/`

负责源码读取、UTF-8 验证、词法分析、语法分析、AST、符号绑定、类型检查、表达式编译、动作程序编译、规则索引建立、隐藏状态分配和带源码位置的诊断。编译完成后运行期只读取不可变编译产物。

### `src/core/`

负责平台无关的控制码、输入事件、动作、值类型、规则、表达式程序、动作程序、任务实例布局和固定容量基础数据。当前 `input_event.hpp` 已改用 `std::uint32_t`、`std::int32_t`、`std::uintptr_t` 及 `ScreenPoint` 等平台无关类型，core 目录不再包含 `windows.h`、`DWORD`、`LONG`、`POINT`、`ULONG_PTR` 或 `VK_*` 依赖。

### `src/runtime/`

负责同步 `RuleDispatcher`、完整映射 `MappingRuntime`、协作式 `TaskScheduler`、表达式求值、运行状态、取消代际、任务容量和输出所有权。低级输入回调必须在返回前得到确定的消费决定，持续动作则在任务线程执行。

### `src/app/`

负责应用生命周期、配置加载与原子切换、运行控制、安全策略、目标状态协调和供 CLI/TUI 读取的不可变状态快照。当前 `AppRuntime`、`RemapEngine` 和 `ActionScheduler` 提供 Phase 1 对应职责，通用运行时实施时可把规则分派、宏任务和注入工作进一步拆开。

### `src/platform/windows/`

负责低级钩子、Win32 到 core 的事件规范化、core 动作到 `INPUT` 的转换、`SendInput`、进程查找、目标进程身份和完整性、前台及指针路由检查、`CreateProcessW` 和 Windows 时钟。当前鼠标 `POINT` 和 Win32 输入字段只在这一层出现并被显式转换。

### `src/ui/tui/`

负责配置选择和验证结果、目标状态、启动、暂停、停止、重新加载、任务状态、输出所有权和诊断查看。TUI 通过 `ApplicationController` 命令和状态快照工作，不进入钩子回调或任务执行热路径。

### `src/diagnostics/`

负责结构化事件、隐私策略、有界缓冲、JSONL 写入、编译诊断、规则匹配解释、任务状态、性能指标和故障信息。当前诊断线程和日志容量机制可以扩展到编译器与通用运行时。

### `src/support/`

只适合容纳真正与领域无关的固定容量容器、结果类型和小型基础设施。队列属于运行时并发，源码区间属于编译器，Win32 转换属于 Windows 平台层；这些内容不应进入宽泛的 `utils` 杂物模块。

## 执行引擎命名

对外模块适合使用 `RuntimeEngine`、`RuleRuntime` 或“规则执行引擎”。内部解释不可变动作程序的部件可以命名为 `ActionVM`，但完整运行系统还包括同步规则分派、映射生命周期、任务调度、取消、目标策略和输出所有权，因此整个模块仅称“解释器”会缩小其真实职责。

## 安全不变量

- 输入来源分类在用户规则之前完成，自身和第三方注入输入不修改物理状态或触发规则。
- 钩子路径不等待、不写文件、不写控制台、不执行外部进程、不执行持续动作，也不依赖无界内存。
- 一次输入事件需要的规则任务以不可拆分批次预留，容量不足时不发布部分任务并放行原输入。
- 每个被消费的完整映射来源都有锁存的目标和可完成的释放路径。
- 程序只为成功发送的合成按下建立输出所有权，取消或停止释放全部实际拥有的输出。
- 队列、任务池、局部帧、诊断和清理记录均有固定上限。
- 强制停止识别独立于目标、配置、暂停和用户规则，并只接受物理候选输入。
- `exec` 配置被视为具有启动外部进程能力的可执行配置，用户界面和配置加载策略需要明确显示该能力。

## 调试和用户交互接口

当前 JSONL、隐私脱敏输入跟踪、队列结果、注入结果、清理结果、熔断状态、最大钩子耗时和退出指标构成运行时调试基础。通用规则运行后，诊断模型适合继续提供源码文件、行列区间、规则编号、条件结果、消费原因、任务编号、程序位置、等待截止时间、取消原因、变量快照和输出所有权快照。

CLI/TUI 可围绕同一个应用控制接口提供配置验证、编译诊断、规则解释、无真实钩子的事件模拟、编译产物导出、运行状态和有界日志查看。运行时错误事件已经为即时显示队列满等故障建立独立于钩子控制台输出的通知路径。

## 实施顺序结论

下一阶段的稳定实施顺序是先确定 Windows v1 能力目录、平台无关控制码和不可变编译产物，再完成 lexer、parser、名称绑定和类型检查；随后以假输入后端和假时钟实现可确定测试的规则分派、完整映射、任务调度、取消和输出所有权，最后接入现有 Windows 钩子与注入底座，并通过应用控制接口连接 CLI/TUI。

每个阶段都应保持严格警告构建、纯编译器测试、确定性运行时测试、容量和取消压力测试、失败注入测试，以及真实 Windows 输入回环验证。
