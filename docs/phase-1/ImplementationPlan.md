# Phase 1 Implementation Plan

## Status

Phase 1 is planned and has not been implemented. The authoritative status is recorded in `AGENTS.md`.

## Objective

Build the smallest end-to-end Windows input pipeline that can observe keyboard and mouse events, classify their origin, emit tagged synthetic input, and prove that the remapper never treats its own output as a new mapping source.

## Scope

### Included

- Install `WH_KEYBOARD_LL` and `WH_MOUSE_LL` hooks on a dedicated message-loop thread.
- Normalize hook data into a common internal event model.
- Classify each event as `PhysicalCandidate`, `SelfInjected`, or `ExternalInjected`.
- Generate one process-specific `ULONG_PTR` self tag and place it in every `KEYBDINPUT.dwExtraInfo` and `MOUSEINPUT.dwExtraInfo` field produced by the program.
- Forward self-injected events to the target application without updating source state or evaluating rules.
- Use a strict default policy in which only non-injected events can trigger diagnostic rules.
- Provide an opt-in hard-coded diagnostic mapping that proves loop prevention without introducing the `.krm` parser.
- Provide a separate input probe executable that records received keyboard, mouse, and raw-input messages.
- Provide bounded asynchronous action and diagnostic queues, controlled shutdown, and fail-open behavior.
- Validate the configured target process and refuse to arm diagnostic suppression when its integrity level is higher than the remapper's integrity level.
- Provide batch files for building and running the Phase 1 executables.
- Provide dependency-free automated tests for pure classification and state-machine behavior.

### Excluded

- `.krm` parsing or a current mapping-language specification.
- General user-defined mappings, macros, loops, variables, expressions, or command execution.
- Mouse position or velocity conditions.
- Configuration reload, tray UI, service installation, UIAccess, or a kernel driver.
- Compatibility workarounds for individual games or anti-cheat systems.
- Production packaging, signing, or automatic elevation.

## Diagnostic Behavior

- Diagnostic mapping is disabled unless the program is started with an explicit diagnostic option and the target process ID owns a foreground window whose class is `UniversalKeyRemapper.Phase1InputProbe`.
- While the target process owns the foreground window, a physical F6 press produces one tagged F7 tap and consumes the paired physical F6 press and release.
- A physical F7 press produces one tagged F8 tap under the same conditions.
- The F7 generated by the F6 rule must be classified as `SelfInjected`, forwarded to the target, and must not trigger the F7-to-F8 rule.
- A physical F9 press produces one tagged middle-button click, while a physical middle-button press produces one tagged F10 tap.
- The middle-button click generated by the F9 rule must be classified as `SelfInjected`, forwarded to the target, and must not trigger the middle-button-to-F10 rule.
- The explicit `--self-test` option starts a visible three-second countdown and then emits one tagged keyboard tap and one tagged relative mouse event only if target integrity validation passed and the foreground window still matches the configured probe PID and fixed class; each batch retains the target PID for the worker's final PID-and-class focus check.
- Injected input carrying another tag is classified as `ExternalInjected`, forwarded, and ignored by the strict diagnostic policy.
- A physical Ctrl+Shift+F12 chord disables diagnostic routing and requests clean shutdown independently of configuration or target focus; the emergency chord itself is forwarded.

## Planned Deliverables

- `bin/UniversalKeyRemapper.exe`: the Phase 1 hook host and diagnostic remapper.
- `bin/InputProbe.exe`: a small Win32 receiver that displays its PID and records traditional and raw input messages.
- `bin/Phase1Tests.exe`: dependency-free automated tests using assertions and fake events.
- `script/build.bat`: the canonical Phase 1 build command.
- `script/test.bat`: the canonical automated Phase 1 test command.
- `script/run_probe.bat`: the canonical input-probe launch command.
- `script/run_remapper.bat`: the canonical diagnostic remapper launch command with a target PID argument.
- `res/UniversalKeyRemapper.manifest`: an explicit `asInvoker` and `uiAccess=false` execution manifest.
- `res/UniversalKeyRemapper.rc`: the resource script that embeds the execution manifest in the remapper executable.
- `docs/phase-1/Verification.md`: created during implementation to record exact build, automated-test, and manual-test results.

## Work Sequence

1. Define normalized fixed-size event, action batch, origin, decision, and captured-input types shared by the Windows adapters and pure tests.
2. Implement pure keyboard and mouse origin-classification functions and verify them with synthetic structures.
3. Implement target-process validation, integrity-level comparison, and the foreground PID guard.
4. Implement the bounded action queue and an injector that writes the self tag into every generated input structure.
5. Implement the dedicated hook thread, message loop, hook installation, callback normalization, and safe unhooking.
6. Implement the fixed keyboard and cross-device diagnostic rules, first-down edge handling, automatic-repeat suppression, paired source capture, and emergency stop chord.
7. Implement asynchronous structured diagnostics without file or console I/O in either hook callback.
8. Implement the input probe and register it for keyboard and mouse Raw Input in addition to traditional window messages.
9. Add the explicit execution manifest and canonical build, test, and run batch files, then compile every executable with the configured MinGW-w64 toolchain.
10. Run automated classification, recursion, state-pairing, queue-capacity, and shutdown tests.
11. Perform the physical-device and integrity-level checks and record the results in `Verification.md`.

## Automated Verification

- A non-injected keyboard event is classified as `PhysicalCandidate`.
- An injected keyboard event with the current self tag is classified as `SelfInjected`.
- An injected keyboard event with another tag is classified as `ExternalInjected`.
- Equivalent cases pass for mouse input.
- A non-injected event carrying a value equal to the self tag remains `PhysicalCandidate`.
- Every generated keyboard and mouse `INPUT` contains the active self tag.
- Diagnostic serialization preserves exact codes only for Phase 1 diagnostic controls and redacts an ordinary letter-key event to `OtherKeyboard` without its virtual key or scan code.
- Feeding physical F6 into the diagnostic engine produces exactly one F7 tap and never produces F8.
- Feeding physical F7 produces exactly one F8 tap.
- Feeding self-tagged F6 or F7 produces no action.
- Feeding physical F9 produces exactly one middle-button click and never produces F10.
- Feeding a physical middle-button press produces exactly one F10 tap.
- Feeding a self-tagged middle-button click produces no action.
- Repeated F6 down events before the matching up event produce only one F7 tap.
- A diagnostic rule is rejected and its source is forwarded when the intended output control is already physically held.
- A queued action is cancelled when the intended output control's published physical-state generation changes before injection or that control becomes physically held.
- A consumed source press causes its matching release to be consumed even if diagnostic mode is disabled between the two events.
- If an action cannot be queued, the initiating source event is forwarded and is not recorded as captured.
- The action and diagnostic rings enforce their documented capacities, reject or drop the next item without blocking, and increment the correct counter.
- Three consecutive short or failed injection results disable new captures, while a successful full send resets the consecutive-failure count.
- The optional JSONL writer stops at its documented byte limit and reports truncation without exceeding the limit.
- Diagnostic suppression cannot arm when target validation fails or the target integrity level is higher than the remapper's integrity level.
- Diagnostic suppression rejects an arbitrary target PID that does not own the expected Phase 1 probe window class.
- Diagnostic routing disables when the retained target-process handle becomes signaled, even if Windows later reuses the numeric PID.
- Shutdown drains or cancels queued work, honors the documented captured-release grace deadline under a fake clock, releases any owned synthetic state, removes both hooks, and terminates all threads.

## Manual Verification

- Confirm that a real keyboard F6 press appears in the probe's traditional-message stream as one F7 press and release, with no F6 or F8 event.
- Confirm that a real keyboard F7 press appears in the probe's traditional-message stream as one F8 press and release.
- Confirm that a real keyboard F9 press appears in the probe's traditional-message stream as one middle-button click with no F10 event.
- Confirm that a real physical middle-button press appears in the probe's traditional-message stream as one F10 press and release.
- Review traditional messages and Raw Input as separate streams; a Raw Input observation of the physical source is not by itself evidence that traditional-message suppression failed.
- Confirm that the tagged keyboard self-test is logged as `SelfInjected` and does not schedule another action.
- Confirm that the tagged mouse self-test is logged as `SelfInjected` and does not schedule another action.
- Confirm that mappings remain inactive when the configured target PID is not in the foreground.
- Confirm that diagnostic startup rejects a normal application PID that does not own the expected Phase 1 probe window class.
- Confirm that the default non-elevated executable works with a normal target and that an elevated target requires an equally elevated remapper because of UIPI.
- Confirm that stopping the program, including while a source key is held, leaves no synthetic key or mouse button stuck.
- Perform diagnostic mapping checks without concurrently pressing the mapped output controls; Phase 1 detects observed state changes before injection but cannot make the final state check and `SendInput` atomically indivisible.
- Exercise sustained keyboard repeat and high-rate mouse movement while recording maximum local hook-processing duration, queue overflow counters, and dropped diagnostic records.

## Completion Gate

Phase 1 may be marked `Complete` in `AGENTS.md` only after all planned source files and batch files exist, all three executables build successfully, `script/test.bat` passes, required manual checks pass, and `docs/phase-1/Verification.md` records the commands and results.

If any required check is unverified, the status must remain `Planned` or `In Progress`; partial implementation is not completion.

## Safety Rules

- The hook path must be fail-open: unexpected states, inactive targeting, rejected events, and diagnostic-queue failures forward input unless a valid paired capture already requires suppression.
- A source event must not be consumed unless its required output action has been accepted by the action queue.
- Because queued injection can still fail after a source event is consumed, target integrity is validated before arming, every send result is checked, and repeated send failures disable new captures.
- Hook callbacks must not sleep, parse files, allocate unbounded memory, write files, flush console streams, wait on worker threads, or call external programs.
- Self-injected and external-injected events must never be suppressed merely because they are ignored as rule sources.
- Diagnostic mode must implement the hard-coded physical Ctrl+Shift+F12 emergency stop path independently of target focus and future configuration files.
- Diagnostic logs must use bounded storage and retain exact codes only for Phase 1 diagnostic controls; all other keyboard codes and scan codes are redacted so persisted output cannot reconstruct arbitrary typed text.
- Low-level hook timeout removal is fail-open and may be silent on supported Windows versions; Phase 1 minimizes callback work and records stress evidence but does not claim that every hook loss can be detected.

## Phase Handoff

When implementation starts, change the Phase 1 status in `AGENTS.md` from `Planned` to `In Progress`. When the completion gate is satisfied, change it to `Complete`, add the completion date, and link the verification record without rewriting the historical design in `legacy/`.
